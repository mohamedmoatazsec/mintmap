### What happens

dj-rest-auth creates its token with `api_settings.TOKEN_CREATOR(...)`. When project code calls it the same way, MintMap reports nothing: no path, no candidate, no gap. In the round-4 evaluation this was one of the general causes of silent misses.

### Minimal snippet

Add to `examples/demo/members/views.py` and route it in `members/urls.py`:

```python
from dj_rest_auth.app_settings import api_settings
from dj_rest_auth.models import TokenModel


class PartnerTokenView(APIView):
    def post(self, request):
        serializer = PartnerSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        token = api_settings.TOKEN_CREATOR(TokenModel, serializer.validated_data["user"], serializer)
        return Response({"key": token.key})
```

```python
path("api/partner-token/", views.PartnerTokenView.as_view()),
```

`mintmap diff examples/demo` still prints `exit 0 (ok)` (checked on 0.6.0a2, whose analysis is that of 0.6.0a1), although the pull request adds a new way to get an API token.

### Acceptance criteria

- [ ] A call through a catalogued library settings object that holds a mint function (`api_settings.TOKEN_CREATOR`, and the equivalent hook settings of the other catalogued libraries) is reported as a path, or at least as a named gap at the call site.
- [ ] The snippet above makes `mintmap diff` exit with `new_path` (bit 1) or `coverage_regression` (bit 32).
- [ ] The catalog entry cites the library source file and line it was read from.
- [ ] A test with a synthetic project, in the style of `tests/test_v6.py`.
