### What happens

MintMap analyses every settings module that a `DJANGO_SETTINGS_MODULE` literal in the project's code names (`manage.py`, `wsgi.py`, `asgi.py`, ...). As alternatives it also analyses every other leaf settings module, meaning one that no other settings module star-imports, except modules named as test settings. The results are merged: lists are united, and values that differ are kept with a `conflicting_setting` gap. There is no way to choose one settings module, or to analyse alone a module that another settings module star-imports. For CVAT the scan analysed `cvat.settings.development` and `cvat.settings.email_settings`, which star-imports `cvat.settings.production`. A verifier re-ran with production-only settings, and no unit changed.

### Minimal snippet

```python
# manage.py
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "shop.settings.dev")

# shop/__init__.py and shop/settings/__init__.py: empty

# shop/settings/base.py
INSTALLED_APPS = ["django.contrib.auth", "django.contrib.sessions", "shop"]
MIDDLEWARE = ["django.contrib.sessions.middleware.SessionMiddleware",
              "django.contrib.auth.middleware.AuthenticationMiddleware"]
ROOT_URLCONF = "shop.urls"

# shop/urls.py
urlpatterns = []

# shop/backends.py
class DevAutoLoginBackend:
    def authenticate(self, request, username=None, password=None):
        return None

# shop/settings/dev.py
from .base import *  # noqa
AUTHENTICATION_BACKENDS = ["shop.backends.DevAutoLoginBackend"]

# shop/settings/prod.py
from .base import *  # noqa
AUTHENTICATION_BACKENDS = ["django.contrib.auth.backends.ModelBackend"]
```

Both `dev.py` and `prod.py` are analysed and merged (checked on 0.6.0a2, whose analysis is that of 0.6.0a1):

```
files parsed 8/8  parse failures 0  settings ['shop.settings.dev', 'shop.settings.prod']  root URLconf ['shop.urls']
  gap conflicting_setting: - AUTHENTICATION_BACKENDS :: differs between settings modules
  gap settings_module_ambiguous: - DJANGO_SETTINGS_MODULE :: shop.settings.dev; also analysed as alternatives: shop.settings.prod
```

`settings:AUTHENTICATION_BACKENDS` then holds both backends. Analysing only `prod.py` is not possible.

A module other than the one `DJANGO_SETTINGS_MODULE` names counts as a settings module only when it, or a module it star-imports, assigns `ROOT_URLCONF`, `MIDDLEWARE`, `MIDDLEWARE_CLASSES` or `INSTALLED_APPS`. Without `base.py`, only `dev.py` is analysed.

### Acceptance criteria

- [ ] `mintmap scan|init|update|diff <dir> --settings shop.settings.prod` analyses that module.
- [ ] The lock records the settings module it was written for, and `diff` with a different module is a `coverage_regression` (changed roots), not a silent pass.
- [ ] The GitHub Action gets a matching `settings` input.
- [ ] Without the option nothing changes: existing locks stay valid.
