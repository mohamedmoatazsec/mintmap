### What happens

When a project loads a function from a dotted path in settings through its own helper, the function's code is not part of any path's fingerprint. Weakening it passes `mintmap diff`.

### Minimal snippet

On a copy of `examples/demo`:

```python
# members/hooks.py
from django.utils.module_loading import import_string


def load_func(dotted_path):
    return import_string(dotted_path)


def office_hours_only(request, member):
    return member.is_active and not member.groups.filter(name="suspended").exists()
```

```python
# teahouse/settings.py
TEAHOUSE_SIGN_IN_GATE = "members.hooks.office_hours_only"
```

```python
# members/views.py, in sign_in()
if member is None or not load_func(settings.TEAHOUSE_SIGN_IN_GATE)(request, member):
    form.add_error(None, "Wrong username or password.")
```

Run `mintmap update` and `mintmap accept --all`. Then change the hook's body to `return True`. `mintmap diff` prints `exit 0 (ok)` (checked on 0.6.0a2, whose analysis is that of 0.6.0a1).

### Acceptance criteria

- [ ] A call of the form `helper(settings.NAME)(...)`, where the helper returns `import_string(...)` (or `importlib.import_module` plus `getattr`), resolves to the function the setting names.
- [ ] That function's code is in the fingerprint of the paths that call it, so the change above raises `fingerprint_changed`.
- [ ] If the setting's value cannot be read statically, a gap names the call site.
- [ ] The same for adapter classes re-exported from a package `__init__`, or a separate issue for them.
